# cs2cinema

## What This Is

cs2cinema — десктопное приложение для Windows (Rust, egui) и CLI `cs2-cli`, которые из демки CS2 (локальный `.dem` или матч FACEIT по ссылке) автоматически делают видеомонтаж: парсят демку, находят моменты игрока, планируют камеры, записывают дубли через HLAE в реальном CS2 и склеивают ролик через ffmpeg. Запись идёт на машине автора, со своим CS2 и HLAE.

С v1.1 у проекта появляется серверная часть: отдельная программа на другой машине с Telegram-ботом. Бот принимает демки от автора и его друзей, сервер раздаёт задачи раннеру (этому приложению или его CLI-режиму), а готовый ролик выкладывает в Telegram.

## Core Value

Задача на монтаж доходит до готового `highlights.mp4` без ручного вмешательства, а если это невозможно — останавливается быстро и объясняет, что именно пошло не так. Для v1.1 то же верно от демки, отправленной боту, до ролика в чате.

## Current Milestone: v1.1 Сервер и Telegram-бот

**Goal:** Принимать демки через Telegram-бота на отдельной машине, отдавать их раннеру на машине с CS2 и возвращать готовый ролик в чат.

**Target features:**
- Серверная программа в этом же Rust-воркспейсе, запускается на другой машине.
- Telegram-бот принимает демку файлом; лимиты Telegram обходятся локальным Bot API (файлы до 2 ГБ).
- Доступ по белому списку Telegram-ID: автор и друзья, одна общая очередь; ролик получает тот, кто прислал демку.
- Игрок закреплён за пользователем бота, меняется командой `/player`.
- Раннер сам подключается к серверу (исходящее соединение), берёт задачу, скачивает демку, ведёт её через `pipeline::job` и загружает `highlights.mp4` на сервер.
- Сервер отправляет в чат результат или понятную причину сбоя (коды и подсказки из `FailCode`).

### Out of Scope

- Публичный открытый бот для всех — доступ только по белому списку автора и друзей
- Несколько раннеров и распределение между ними — один раннер, одна запись за раз; расширение позже
- Улучшение режиссуры и качества монтажа — пока не стабильна цепочка бот → сервер → раннер
- Linux/macOS для раннера — HLAE и запись CS2 работают только на Windows (сервер может быть на другой ОС)
- Публичный релиз, установщик, английский интерфейс
- Долги v1.0: приёмка на 5 матчах (04-12), учения D1–D6 (ACC-02, ACC-03), проверка трея и кириллицы в уведомлении (A1/A3), подтверждение фикса стабильности дубля на живой записи — остаются в архиве v1.0, вернуть можно отдельным решением; первый сквозной прогон v1.1 станет живой проверкой записи

## Context

- Карта кодовой базы: `.planning/codebase/` (обновлена в фазе 4 v1.0).
- v1.0 «Надёжность записи» закрыт с открытыми пробелами: фазы 1–3 выполнены и проверены, фаза 4 (очередь без присмотра) выполнена кроме приёмки 04-12 и ручных учений. Подробности — в архиве `milestones/v1.0-phases/` и в `04-11-SUMMARY.md`.
- Ограничения Telegram: облачный Bot API отдаёт боту файлы до 20 МБ и принимает до 50 МБ. Демки CS2 — сотни мегабайт, ролики больше 50 МБ. Поэтому на сервере поднимается локальный `telegram-bot-api` (лимит 2 ГБ).
- Раннер — это текущее приложение (или CLI): он подключается к серверу сам, поэтому машина с CS2 может быть за NAT без проброса портов.
- Типичный сбой записи по-прежнему «игра не стартует»; причина доходит до пользователя бота как код и подсказка.
- Интерфейс, журналы и сообщения бота — на русском; идентификаторы в коде — на английском.
- Внешние зависимости: HLAE, CS2 через Steam, `ffmpeg`/`ffprobe`, FACEIT Data API, Telegram Bot API (локальный `telegram-bot-api`).

## Constraints

- **Tech stack**: Rust cargo workspace, `std::thread`, SQLite через rusqlite. Для сервера и бота допустимо отступление (например, `tokio` и HTTP-клиент для Bot API), если стандартных потоков недостаточно; решает исследование v1.1 и записывается в Key Decisions
- **Platform**: раннер только Windows; сервер должен собираться и работать на машине, которую автор выберет (ОС пока не задана)
- **External tools**: HLAE и CS2 — внешние процессы с недокументированными маркерами консоли; любой детектор имеет таймаут и диагностику
- **Concurrency**: одна запись за раз на раннере
- **Compatibility**: `cs2-cli` собирается и проходит `crates/cli/tests/pipeline.rs`; приложение продолжает работать автономно без сервера
- **Security**: токен бота, ключ FACEIT и токены раннеров не попадают в журналы и в репозиторий; доступ к боту по белому списку
- **Language**: пользовательские строки на русском

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| v1.0 целиком про надёжность записи, а не про качество монтажа | Главная боль — запись не стартует, причина неясна | ✓ Good (код и тесты); живая приёмка не проведена |
| Архитектуру можно перестраивать (запись и сборка в `pipeline`, процессы за `Host`) | Иначе сценарии отказов не покрыть тестами | ✓ Good |
| Приоритет у приложения, CLI только не ломать | Пользователь гоняет монтажи из приложения | ✓ Good |
| Долги приёмки v1.0 остаются в архиве, не переносятся | Решение автора при старте v1.1: проверим живой записью на первом сквозном прогоне | — Pending |
| Раннер сам подключается к серверу | Машина с CS2 может быть за NAT; не нужен входящий порт | — Pending |
| Локальный `telegram-bot-api` вместо облачного | Облачные лимиты 20/50 МБ не подходят демкам и роликам | — Pending |
| Белый список «автор и друзья», игрок закреплён за пользователем (`/player`) | Решение автора при старте v1.1 | — Pending |
| Сервер — `tiny_http` 0.12 на `std::thread`, без tokio (D-01) | Спайк фазы 5 прошёл: PUT по 8 МиБ, `Expect: 100-continue`, обрыв тела; закреплено тестами `crates/server/tests/transfer_http.rs` и `protocol_http.rs`. Приняты ограничения: нет таймаутов сокета (ограниченный пул + 503, таймауты — на прокси впереди), недочитанное тело дочитывается в `Drop` (все отказы — до `as_reader`, 503 из отдельного потока), обрыв тела выглядит как чистый EOF (сверка принятых байтов с `Content-Length`); `SO_KEEPALIVE` на слушающем сокете не включали. Выход — `axum` 0.8 + `tokio` только в `crates/server`, если зависшие клиенты станут проблемой на деле или раннеров станет больше одного | ✓ Good (фаза 5) |
| База сервера — `Arc<Mutex<rusqlite::Connection>>` (rusqlite 0.32.1), WAL, `BEGIN IMMEDIATE`, миграции через `user_version` (D-04) | Одно соединение под мьютексом сериализует запросы процесса; `cs2-server submit` — второй процесс на том же файле, поэтому `BEGIN IMMEDIATE` и `busy_timeout`; мьютекс не держится во время работы с файлами и хеширования; поток-актор не понадобился | ✓ Good (фаза 5) |
