## Phase Goal

**As a** автор, который держит сервер очереди монтажа на Linux-машине, **I want to** ставить демку в очередь командой `cs2-server submit`, выдавать раннеру токен и видеть, как задача выдаётся с арендой и эпохой, переживает обрывы и приносит результат кусками с проверкой SHA-256, **so that** цепочка «демка → сервер → раннер → ролик» проверяется без Telegram и без CS2, а токены не утекают в журналы.

<objective>
Второй срез: раннер входит по токену и забирает задачу по HTTP. `cs2-server serve` на `tiny_http` 0.12 (D-01): поток-диспетчер, фиксированный пул обработчиков и 503 при переполнении (D-02), адрес из настроек (D-03), атомарная выдача с эпохой одной транзакцией под мьютексом (D-04), long-poll `claim`, отказ 401 для чужих и отозванных токенов, журнал запросов через `Redactor`, остановка по Ctrl+C/SIGTERM. Тесты протокола — через настоящий HTTP на localhost (D-05).

Purpose: после плана тестовый клиент протокола забирает задачу, поставленную `submit`, — первый сквозной путь «оператор → сервер → раннер».
Output: `http.rs`, `api.rs`, `log.rs`, `Core::claim`, `serve`/`Running`, команда `serve`, общий тестовый стенд `tests/common/mod.rs`, `tests/protocol_http.rs`.

Спайк D-01 выполнен на этапе исследования (05-RESEARCH.md, «Summary» и «Common Pitfalls»): `tiny_http` прошёл, запасной выход на `axum` не нужен. Его случаи закрепляются тестами: пул и 503 — здесь, PUT по 8 МиБ, `Expect: 100-continue` и обрыв тела — в 05-05; там же решение записывается в Key Decisions.
</objective>
