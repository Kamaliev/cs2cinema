## Phase Goal

**As a** автор, который держит сервер очереди монтажа на Linux-машине, **I want to** ставить демку в очередь командой `cs2-server submit`, выдавать раннеру токен и видеть, как задача выдаётся с арендой и эпохой, переживает обрывы и приносит результат кусками с проверкой SHA-256, **so that** цепочка «демка → сервер → раннер → ролик» проверяется без Telegram и без CS2, а токены не утекают в журналы.

<objective>
Пятый срез: файлы кусками по 8 МиБ (SRV-06). Загрузка результата `HEAD` + `PUT` с `Upload-Offset` (длина `.part` на диске — единственная правда о смещении, `.part` своя у каждой эпохи), итог `done` с проверкой размера и SHA-256, скачивание демки по `Range`. Три слабости `tiny_http` из исследования обходятся здесь в обработчиках: отказ до `as_reader` (нет `100 Continue`, тело не дочитывается зря), сверка принятых байтов с `Content-Length` (обрыв выглядит как чистый EOF), ответы больше 32 КиБ с настоящим `Content-Length`. Решение по HTTP-стеку и модели базы записывается в Key Decisions.

Purpose: после плана раннер фазы 6 может скачать демку и надёжно отдать `highlights.mp4` даже через обрывающуюся связь, а неверный файл никогда не становится результатом.
Output: загрузка и скачивание в `api.rs`/`blobs.rs`/`core.rs`, `Outcome::Done`, `tests/transfer_http.rs`, строки в `.planning/PROJECT.md`.

**Решения на усмотрение Claude (исследование Pattern 5, «Alternatives Considered», Open Question 2):** протокол — свой `HEAD`-смещение + один кусок на запрос (без tus/multipart); полный SHA-256 пересчитывается при `finish` (переживает перезапуск сервера, в отличие от состояния хеша между кусками); частично принятый кусок сохраняется; загрузки демки по HTTP нет — `submit` локальный, бот фазы 7 кладёт файл на месте.
</objective>
