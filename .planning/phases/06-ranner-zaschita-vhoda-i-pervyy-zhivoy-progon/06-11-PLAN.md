## Phase Goal

**As a** автор с CS2 на своей машине, **I want to** запустить `cs2-cli runner`, который сам забирает задачи с `cs2-server`, безопасно разбирает чужие демки и ники и возвращает `highlights.mp4` на сервер с подтверждёнными размером и SHA-256, **so that** друзья могут присылать демки, а любой отказ объясняется своим кодом ещё до запуска CS2.

<objective>
Первый живой прогон настоящей демки через сервер, раннер и настоящие CS2 + HLAE на машине автора и учения на отмену, обрыв, чужой CS2 и враждебные входы. Прогон неформально закрывает долг v1.0 по живой проверке записи (фикс стабильности дубля); приёмка 04-12 не возобновляется.

Purpose: критерии успеха фазы 1-5 подтверждаются уликами, а не только тестами на `FakeHost`; стартовые лимиты разбора и дедлайны записи калибруются по замерам.
Output: `06-LIVE-RUN.md` и папка `evidence/` (только текст: журналы, снимки, хеши), при необходимости поправленные значения по умолчанию.

**Решения (решение оркестратора 5; CONTEXT Specific Ideas; исследование «Подход к тестам: живой прогон», Pitfall 12; Open Questions 2, 4, 6):**
- Это план с участием автора (`autonomous: false`): демку скачивает автор (ключ FACEIT — у автора), CS2 запускается на его экране. Шаги проверки глазами собраны в `<human-check>` (режим `end-of-phase`).
- Данные сервера и папка раннера — вне репозитория: `%LOCALAPPDATA%\cs2cinema\live-06\{server,runner}` (демки и ролики в git не попадают). В папку фазы копируются только текстовые улики.
- Сервер слушает `127.0.0.1:8787` (loopback): дефект CR-01 сервера при этом не опасен (исследование, Open Question 8).
- Калибровка: если пиковая память разбора больше половины лимита 6 ГиБ или какая-то стадия записи заняла больше 70 % своего дедлайна, значение по умолчанию поднимается (`crates/cli/src/runner_cmd.rs` или `crates/pipeline/src/record/deadlines.rs`) с записью причины; иначе код не меняется.
- `tasklist` и `taskkill` — **только инструменты учений**: исполнитель этого плана набирает их в консоли Git Bash, чтобы видеть процесс `cs2.exe` (D1, D4) и «убить» процесс раннера (D2). В код продукта они не попадают ни в одном крейте: с фазы 4 процессы игры видны только через `host::Host` и Job Object, а калибровочные правки этого плана (`runner_cmd.rs`, `deadlines.rs`) меняют только числа. Проверка — `grep` по `crates/` в `<verify>` Task 3.
- Строки `job show`, на которые опираются проверки: `состояние: {название} ({код})` печатает уже существующая `print_job` (`crates/server/src/cli.rs`; названия — `wire::JobState::title`: `Done` → «готово», `Queued` → «в очереди», `Cancelled` → «отменена»), то есть после успешной задачи выводится `состояние: готово (done)`; строки `этап:`, `дубль:` и `результат:` добавляет план 06-09.
- Граница отмены (D1): мягкая отмена закрывает игру через `quit` (`quit_wait` 5 с), а если задача за `FORCE_AFTER` = 10 с не закончилась, раннер сам переводит её в жёсткую (план 06-08); итого `cs2.exe` должен исчезнуть не позже чем через 20 с после `job cancel`.
- Выдачи (D4): `release` всегда засчитывает выдачу (D-02 буквально, решение автора при ревизии планов): после двух сбоев подряд раннер на паузе, а третья неудачная выдача закончилась бы на сервере `TOO_MANY_GRANTS`.
</objective>
