# Phase 6: Code Review Report

**Reviewed:** 2026-10-11
**Depth:** standard
**Files Reviewed:** 28 (тесты читались выборочно, только на предмет ожиданий по очистке файлов)

## Summary

Просмотрены раннер (outbox, повторы, отмена, пульс, загрузка/докачка), дочерний разбор демки и его песочница, пределы
чтения демки, очистка недоверенного текста, вынос подписей ffmpeg в файлы, проверка итогового ролика, выбор игрока.
Общий вывод: защита входа сделана добросовестно (токен нигде не печатается, подписи не доходят до cfg и графа,
ответ дочернего процесса не принимается на веру, `decompress_len` ограничен, `stale_epoch` и отмена по порядку
приоритетов обработаны). Блокирующих дефектов не найдено. Основные риски: лимиты, заданные флагами раннера, не доходят
до `run_job`; демка повторно разбирается в самом процессе раннера без песочницы; успешные задачи не чистят диск;
сбой авторизации на `finish`/`release` не останавливает раннер; токен наследуется всеми дочерними процессами;
буферизация строк дочерних процессов не ограничена вопреки комментариям.

## Warnings

### WR-01: Лимиты демки из флагов раннера не доходят до `run_job`; демка повторно разбирается в процессе раннера

**File:** `crates/pipeline/src/job.rs:514` (также `crates/cli/src/runner_cmd.rs:155-161,190`, `crates/runner/src/exec.rs:105-113,220`)
**Issue:** `--max-demo-mib` и `--max-unpacked-mib` попадают только в `InspectLimits` дочернего процесса. Сам `run_job`
вызывает `analyze_with(&src, &demo::DemoLimits::default(), p)` с зашитыми 2000 МиБ / 3 ГиБ. Если автор поднимет
потолок (демка 2.5 ГиБ распакованной), дочерний разбор её пропустит, а `run_job` закроет задачу `DEMO_TOO_LARGE`
уже после предпроверки. Кроме того, этот повторный разбор идёт в самом процессе раннера, без Job Object и без
сторожа времени. Это ровно тот код, от которого дочерний процесс должен был изолировать раннер. Пока парсер
детерминирован, прошедшая проверку демка пройдёт и здесь, но падение/зависание, не воспроизводимое в ребёнке
(другая память, `flybys`), снова валит раннер, а не одну задачу.
**Fix:** Добавить `demo_limits: DemoLimits` в `JobConfig` (или `JobSpec`), заполнять из `args.limits.demo` в
`runner_cmd` и использовать в `run_job`:
```rust
let mut a = crate::analyze_with(&src, &cfg.demo_limits, p)?;
```

### WR-02: Случайный Enter во время работы снимает паузу раннера немедленно

**File:** `crates/runner/src/lib.rs:310` (поток stdin: `crates/cli/src/runner_cmd.rs:314-324`)
**Issue:** `Control::resume` ставит флаг `resume`, который никто не гасит, пока раннер не на паузе. Любое нажатие Enter
(или перевод строки из перенаправленного stdin) во время задачи оставляет флаг взведённым. Когда вторая одинаковая
неисправность затем ставит раннер на паузу, следующий `tick` делает `self.resume.swap(false) && self.paused.take()`
и снимает паузу сразу. Защита от бесконечного круга «неисправность - повтор» (D-02) обходится случайным нажатием.
**Fix:** Принимать `resume` только когда раннер на паузе, а флаг сбрасывать при входе в паузу:
```rust
fn start_pause(&mut self, reason: PauseReason) {
    self.resume.store(false, Ordering::SeqCst); // Enter, нажатый до паузы, не считается
    ...
}
```

### WR-03: Успешные задачи не освобождают диск: демка и папка `out/srvN` остаются навсегда

**File:** `crates/runner/src/lib.rs:961-965` (также `:1004`, `:1047-1062`)
**Issue:** `remove_files` вызывается только при `drop`, `release` и отмене. После `TransferEnd::Done` (результат принят
сервером) не удаляются ни `remote/srvN.dem` (до 2000 МиБ), ни `out/srvN/` с сырыми дублями, ни `highlights.mp4`.
При отказе (`Failed`) демка тоже остаётся. Автономный раннер, который должен работать без присмотра, заполнит диск и
упадёт на записи дублей («нет места»). Тесты не проверяют очистку после успеха.
**Fix:** После подтверждённого `Done` удалять демку и `out_dir` (хотя бы клипы), а для сбоев хранить ограниченное число
последних задач (например, 5) и чистить остальные при старте.

### WR-04: Сбой авторизации (401) на `finish`/`release` не останавливает раннер и повторяется бесконечно

**File:** `crates/runner/src/lib.rs:1013-1019,1063-1069` (также `transfer.rs:141-158`)
**Issue:** `run` останавливается на `TOKEN_REJECTED` только для ошибок, прошедших через `link_error` (claim, hello).
`report()` и `release()` оборачивают ошибку как `format!("задача #{id}: finish: {e}")`, а `judge` для 401 даёт `Retry`.
На этапе `Reporting` пульса нет (он остановлен), поэтому отзыв токена там обнаруживается только `finish`: раннер вечно
шлёт запрос с паузой до 30 с и пишет `ошибка: ...` в журнал, а итог задачи не доходит до сервера. Это противоречит
заявленному поведению «токен не принят, раннер остановлен, задача остаётся в состоянии».
**Fix:** В `report()` и `release()` пропускать `LinkError::Status{status:401,..}` через `link_error`, чтобы `run` увидел
`TOKEN_REJECTED` (при 401 возвращать ровно `tee::TOKEN_REJECTED`, а не обёрнутую строку).

### WR-05: Любой 404/409 без кода трактуется как окончательный отзыв задачи и удаляет результат

**File:** `crates/runner/src/transfer.rs:141-158`, `crates/runner/src/tee.rs:34-60`
**Issue:** `judge` и пульс считают `status == 404` и `409 && error.is_empty()` окончательным отказом. Такой ответ может дать
обратный прокси, балансировщик или неправильный базовый путь во время перенастройки, то есть временную неисправность. В
этом случае `drop_job` удаляет готовый `highlights.mp4` и демку (час записи CS2), а `Shared.mark_lost` заставляет
исполнитель немедленно сворачиваться с жёсткой отменой. Допустимо считать окончательными только ответы с известным
телом `ApiError` (`stale_epoch`, `job_terminal`, `not_found`).
**Fix:** Для 404/409 без распознанного `error` возвращать `Retry` (или считать окончательным после N подряд одинаковых
ответов). Для `HEAD` без тела опираться на заголовок кода, если сервер его выставляет.

### WR-06: Тело ответа демки не ограничено, сбой записи на диск выдаётся за сетевой и повторяется вечно

**File:** `crates/runner/src/link.rs:52-53`, `crates/runner/src/transfer.rs:219-227`
**Issue:** `io::copy(&mut reader, out)` копирует тело ответа целиком, потолок `max_demo_bytes` проверяется только по
заявленному `demo_size` из выдачи. Сервер (или прокси), приславший больше заявленного, пишет на диск произвольно много
до конца ответа, и лишь потом `have != size` отправляет в повтор. Ошибка записи (диск полон, `HashingFile::write`)
превращается через `self.net(...)` в «нет связи с сервером: чтение демки», `fetch` возвращает `Err`, и раннер повторяет
тик с паузой до 30 с бесконечно, без heartbeat на время паузы и без сообщения серверу.
**Fix:** Ограничить чтение `reader.take(size - have)` и отличать ошибку записи от ошибки чтения: при ошибке записи закрывать
задачу `JOB_ERROR` (или возвращать через `release`) с понятной причиной «нет места на диске».

### WR-07: Токен раннера наследуется всеми дочерними процессами (разбор демки, ffmpeg, HLAE, CS2)

**File:** `crates/cli/src/runner_cmd.rs:115`, `crates/host/src/runner.rs:57-69`
**Issue:** Токен читается из `CS2_RUNNER_TOKEN` и остаётся в окружении процесса. `run_bounded` не вызывает `env_remove`/
`env_clear`, а `CmdSpec` не имеет поля окружения, поэтому дочерний `cs2-cli inspect` (разбирающий недоверенные байты),
ffmpeg, ffprobe, HLAE и CS2 получают токен. Для ребёнка с урезанной песочницей это лишняя поверхность: уязвимость
парсера открывает токен. Файл `--token-file` этого не страдает.
**Fix:** Добавить в `CmdSpec` список `env_remove` (минимум `CS2_RUNNER_TOKEN`) и применять его в `run_bounded` и при запуске
игры; либо сразу после чтения токена снимать переменную до запуска потоков.

### WR-08: Построчный буфер дочернего процесса не ограничен, хотя комментарии это обещают

**File:** `crates/host/src/runner.rs:30-43` (используется `crates/pipeline/src/inspect.rs:284-297`)
**Issue:** `spawn_reader` читает `read_until(b'\n')` в неограниченный `Vec`, а канал `mpsc::channel` тоже без границы. В
`preflight` комментарий «вывод ребёнка не растёт в памяти» и `REPLY_MAX` режут только уже полностью прочитанную строку.
Ребёнок, который под влиянием враждебной демки напечатает гигантскую строку без перевода строки (паника с огромным
сообщением, отладочный вывод), вырастит память раннера (процесс без лимита) вплоть до дедлайна 15 минут. То же для
stderr (`STDERR_TAIL` хранит 20 строк, но неограниченной длины) и для ответа ffprobe.
**Fix:** Читать порциями с верхним пределом длины строки (например, 256 КиБ), остаток строки отбрасывать:
```rust
let mut limited = (&mut r).take(MAX_LINE);
limited.read_until(b'\n', &mut buf)
// если строка не закончилась переводом строки: дочитать и выбросить хвост
```

### WR-09: Адрес сервера по `http://` отправляет токен открытым текстом без предупреждения

**File:** `crates/runner/src/link.rs:132-137`
**Issue:** `Link::new` принимает любой `http://`-адрес, и заголовок `Authorization: Bearer ...`, демки игроков и результаты
уходят без шифрования, в том числе на публичный сервер. Для `127.0.0.1` это нормально, для остального нет.
**Fix:** Разрешать `http://` только для loopback/частных адресов (или за явным флагом `--insecure-http`), иначе возвращать
ошибку «используйте https://».

## Info

### IN-01: Ctrl+C не прерывает длинный `claim`; взятая в этот момент задача остаётся «держимой»

**File:** `crates/runner/src/lib.rs:322-325`
**Issue:** `claim` блокируется до `poll_secs + 15` с. Остановка в это время обрабатывается только после ответа; если сервер
успел выдать задачу, раннер её принимает, записывает в outbox и сразу останавливается (`Tick::Stopped`), выдача
сгорает до следующего запуска или истечения аренды.
**Fix:** Не принимать выданную задачу при взведённом `stop` (сразу `release` без засчёта) либо пускать запрос с коротким
таймаутом при остановке.

### IN-02: Переполнение при разборе числовых флагов раннера

**File:** `crates/cli/src/runner_cmd.rs:157,161,165,190`
**Issue:** `n << 20` и `n * 60` не проверяют переполнение: огромное значение даёт «обёрнутое» (в release) или паникующее (debug)
число; `--max-demo-mib 18014398509481984` превратится в 0. В `inspect.rs` для тех же флагов уже стоит `saturating_mul`.
**Fix:** Использовать `checked_shl`/`saturating_mul` или отвергать значения выше разумного потолка.

### IN-03: Предпроверка и `run_job` выбирают игрока по разному представлению ника

**File:** `crates/pipeline/src/inspect.rs:113` против `crates/runner/src/exec.rs:109,160`
**Issue:** Ребёнку уходит `clean_text(nick, 256)`, а `run_job` выбирает героя по необрезанному `task.hero_name`. Ник с управляющими
символами или длиннее 256 символов даёт в ребёнке одно совпадение, в `run_job` другое (в худшем случае `PLAYER_NOT_FOUND`
уже после проверки). Практически маловероятно, но две проверки должны видеть одно и то же.
**Fix:** Очищать ник один раз при построении `Task`/`HeldJob` и передавать всюду одно и то же значение.

### IN-04: Две разные функции `clean_text` с одинаковым именем

**File:** `crates/pipeline/src/record/failure.rs:344-351` и `crates/cs2/src/text.rs:19-37`
**Issue:** Версия в `failure.rs` убирает только управляющие символы (bidi-переопределения и невидимые символы остаются), версия
в `cs2::text` убирает и их. Тексты сбоев с запросом пользователя (`query`) проходят через слабую; такой текст попадает в
журнал сервера и карточки.
**Fix:** Использовать `cs2::text::clean_text` и там, оставив в `failure.rs` только добавление `…` при обрезке.

### IN-05: `judge_result` пропускает видео с неизвестными размерами кадра

**File:** `crates/pipeline/src/assemble.rs:73-78`
**Issue:** `width`/`height` берутся через `unwrap_or_default()`; ролик без размеров (ffprobe их не отдал) считается годным и
пишется в журнал как «0x0».
**Fix:** Возвращать `Err("не определён размер кадра")`, если любое значение отсутствует или равно 0.

### IN-06: Синтетические демки и zstd-бомба компилируются в продуктовую библиотеку

**File:** `crates/demo/src/lib.rs:5`
**Issue:** `pub mod synth;` подключён без `cfg(test)` или feature, хотя комментарий говорит «в продукте не используется». Лишний
код и зависимость `prost::Message` в каждом бинарнике.
**Fix:** Закрыть модуль feature `synth` (включать из dev-dependencies тестов крейтов).

### IN-07: `runner.log` растёт без ограничения

**File:** `crates/runner/src/lib.rs:121-148`
**Issue:** Журнал открывается с `append` и не ротируется; при долгой автономной работе и подробных записях (пульс, повторы
каждые 30 с при простое сети) файл растёт неограниченно.
**Fix:** Ротация по размеру (например, 10 МиБ, хранить 3 файла).
