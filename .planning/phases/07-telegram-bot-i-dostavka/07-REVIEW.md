# Phase 7: Code Review Report

## Summary

Разобраны файлы фазы 7 по списку из заданий: клиент Bot API (`tg/`), автомат бота (`bot/`), `db.rs`, `http.rs`, `core.rs`,
`secret.rs`, строгий разбор ссылки FACEIT (`wire/src/faceit.rs`) и исполнитель раннера (`runner/src/exec.rs`).
`users.rs` прочитан как зависимость белого списка (его в задании не было, но проверки доступа живут там).
`tg/fake.rs` (тестовый двойник) и `vendor/tiny_http` не ревьюились. Тесты не запускались.

Что проверено отдельно по заявленному упору и оказалось в порядке:

- **Белый список.** `dispatch::decide` отсекает всё, кроме личного чата и `from.id` активного пользователя, до разбора документа,
  подписи и текста. Роль берётся только из базы; `/adduser` создаёт только `member`, `/removeuser` не трогает админа,
  повысить права из чата нельзя. Обхода по `chat.id`/`forward_origin`/`@имя_бота`/подписи на `/команду` не найдено.
- **Утечка токена.** Токен живёт в `Secret` и в URL запроса `HttpTg::call`; любой текст ошибки проходит `scrub`
  (точный токен, форма с `~`, `Redactor`). `Debug` у `HttpTg`/`Secret` скрыт, `TgError::Display` не печатает `detail`,
  путь из `getFile` (с токеном) нигде не логируется и не уходит в чат: ошибки приёма сводятся к фиксированным классам.
  Прокси из окружения и редиректы у клиента выключены.
- **SSRF.** Адрес bot-api принимается только как `http://` на loopback с портом; в `sendVideo`/`sendDocument` уходит
  `file:///` из числового id и префикса оператора либо `file_id`, полученный от Telegram. Сервер по ссылкам FACEIT не ходит,
  раннер получает только канонический вид из id; `room_match_id` строгий (ASCII, хост целиком, без порта/логина/хвостов).
- **Гонки дублей приёма.** Повтор обновления гасится `UNIQUE(chat_id, message_id)` + смещение в одной транзакции,
  лимиты считаются в той же транзакции, что и вставка, один поток приёма, три слоя поиска дублей.

Найденное ниже в основном про потерю результата и про места, где проверка есть в одном пути, но отсутствует в соседнем.

## Critical Issues

### CR-01: Проверка пути из `getFile` ломает приём файлов на Windows-сервере с bot-api в другой системе

**File:** `crates/server/src/bot/ingest.rs:437-440`
**Issue:** `safe_local_path` начинается с `Path::new(file_path).is_absolute()`. На Windows путь вида `/var/lib/telegram-bot-api/...`
(bot-api в Docker/WSL, именно для этого есть `bot_api_files_root_local`) абсолютным **не считается**: нужен префикс диска.
При этом конфиг (`config.rs:493-496`, `is_abs`) нарочно принимает `has_root()`: «на Windows принимается и вид `/var/lib/…`»,
и `validate` пропускает такую настройку. Итог: сервер стартует, бот отвечает, но каждая присланная демка отвергается
с «проверка пути не пройдена» (`PATH_REJECTED_TEXT`), а в журнале только «путь не абсолютный». Приём файлов в этой поддерживаемой
конфигурации не работает вообще; ссылки FACEIT идут мимо `getFile` и работают, поэтому поломка маскируется.
Это единственный условный дефект уровня «функция не работает», остальные проверки пути (компоненты, символьные ссылки, размер) верны.
**Fix:**
```rust
// ingest.rs: то же правило, что и в config::is_abs
if !(p.is_absolute() || p.has_root()) {
    return Err("путь не абсолютный");
}
```
Вынести `is_abs` в общее место (например, `crate::config::is_abs` как `pub(crate)`) и вызывать из обоих мест; добавить тест
`safe_local_path` с путём `/var/lib/bot-api/x/documents/f.dem` и `files_root_local` на Windows-стиле (под `#[cfg(windows)]`).

### CR-02: `/retry` может потерять доставку ролика: задача ставится раньше, чем создаётся `tg_jobs`

**File:** `crates/server/src/bot/commands.rs:367-393`
**Issue:** `bot.core().resubmit(id, ...)` создаёт и ставит в очередь новую задачу, затем идёт сетевой вызов `bot.say(...)`
(до 30 с на `control`-таймаут), и только после него `store::insert_tg_job`. Доставка (`promote_done` → `deliver_once`)
и уведомления работают только для задач, у которых есть строка `tg_jobs`. Если процесс остановят или упадёт в это окно,
либо `insert_tg_job` вернёт ошибку, задача отработает, ролик будет записан и смонтирован, но другу не придёт ничего:
строки во `tg_inbox` у такой задачи нет, поэтому `own_job` её не подхватит, а `/resend` отвечает «поставлена не через бота».
Ветка ошибки к тому же сообщает «ход её в чате показывать не смогу», умалчивая, что и результат не доставится.
Для приёма файла эта проблема решена (`mark_queued` в одной транзакции, восстановление через `tg_inbox`), для `/retry` — нет.
**Fix:** сначала создать `tg_jobs` (с пустым статусом и `status_message_id = NULL`), потом отправить сообщение и дописать номер:
```rust
let new_id = bot.core().resubmit(id, &user.name)?;
store::insert_tg_job(db, &NewTgJob { job_id: new_id, chat_id, user_id: user.id,
    status_message_id: None, status_text: "", next_edit_ms: 0 }, now)?;   // до любых вызовов Telegram
let message_id = bot.say(chat_id, &text);
if let Some(mid) = message_id { store::set_status_message(db, new_id, mid, &text, now + edit_ms, now)?; }
```
Тик уведомлений сам пришлёт сообщение статуса, если `status_message_id` пуст. Если `insert_tg_job` не удался, сразу
`core.cancel(new_id, true)` и честный ответ «не получилось поставить задачу».

## Warnings

### WR-01: Дубли ищутся по всем пользователям, а `/resend` разрешён только владельцу: второй друг упирается в тупик

**File:** `crates/server/src/bot/ingest.rs:111-126` (текст), `crates/server/src/core.rs:523-560` (`find_duplicate`), `deliver.rs:279-281`
**Issue:** `find_duplicate` не фильтрует по `user_id`. Если ролик по этому матчу/файлу и игроку уже готов у друга A, друг B получает
«Ролик по этому матчу для игрока X уже готов: /resend 12», а `/resend 12` отвечает «Это не ваша задача». Получить ролик B
не может ни при каком действии (задача не ставится, чужую слать нельзя). Тот же ответ раскрывает B номер чужой задачи.
Два друга из одной команды, которым нужен один и тот же игрок, — обычный случай.
**Fix:** для готовых (`done`) дублей чужого пользователя не отказывать, а ставить свою задачу (`submit_from`/`submit_faceit`);
активный дубль другого пользователя можно оставить отказом, но без номера: «Этот матч для этого игрока уже в очереди».
Минимум: в `duplicate_text` не предлагать `/resend` и не показывать номер, если `job.user_id != Some(user.id)`.

### WR-02: После перезапуска «неясная» доставка остаётся молчаливой

**File:** `crates/server/src/bot/store.rs:553-571`, `crates/server/src/bot/mod.rs:210-218`
**Issue:** `recover` переводит `sending` → `uncertain` и пишет только число в журнал. В обычном пути (`fail_delivery`) друг получает
«Не уверен, что ролик дошёл… /resend N», а здесь — ничего: ролик мог не дойти, друг не знает об этом и не знает про `/resend`,
админу тоже не сообщается. `final_reported_ms` остаётся пустым, но ни один тик за `uncertain` не отвечает.
**Fix:** в `recover` возвращать id затронутых задач и после старта рассылать то же сообщение через `deliver::tell`
(либо добавить `uncertain` с `final_reported_ms IS NULL` в кандидаты тика уведомлений).

### WR-03: `/retry` не проверяет дубли и повторную постановку

**File:** `crates/server/src/bot/commands.rs:333-393`
**Issue:** повтор делается без `find_duplicate` и без проверки, что у этой упавшей/отменённой задачи уже есть успешный или идущий повтор.
`/retry` без номера всегда берёт самую свежую упавшую задачу, поэтому два вызова подряд (и даже один после уже запущенного повтора)
ставят две одинаковые задачи, а каждая — это полный запуск CS2 на машине автора. Лимит 2 активных задачи на друга только ограничивает масштаб.
**Fix:** перед `resubmit` вызвать `bot.core().find_duplicate(&DedupKey::...)` по хешу демки/ссылке и игроку и отвечать «уже в очереди/готово»
(та же логика, что у `precheck`); для `/retry` без аргумента выбирать задачу, у которой нет более новой активной с тем же ключом.

### WR-04: Ник из подписи и после ссылки не проходит `valid_player`

**File:** `crates/server/src/bot/ingest.rs:79-90` (`choose_player`), `157-166`; `crates/server/src/core.rs:281`
**Issue:** `/player` и `/adduser` отвергают ники длиннее 64 символов, с управляющими и bidi-символами. Ник из подписи к файлу и
остаток после ссылки FACEIT идёт только через `Redactor::clean(…, 64)`, а он оставляет `\n`, `\t`, U+202E/U+2066 и т. п. и **молча обрезает**
длинную строку до 63 символов + «…». Последствия: подпись-предложение («вот моя игра, ник s1mple») становится игроком-обрубком и
задача падает с `PLAYER_NOT_FOUND` после полного прохода предпроверки; перенос строки/RLO в нике попадает в «Сбой задачи #N (… игрок …)»
у админа и в статусы (подделка строк в сообщении).
**Fix:** `choose_player` для подписи/остатка вызывать `commands::valid_player` и при ошибке отвечать причиной (как `/player`);
не обрезать, а отказывать.

### WR-05: Любая ошибка `getFile` отвергает входящее навсегда

**File:** `crates/server/src/bot/ingest.rs:746-749`
**Issue:** `Err(e) => return reject(...)` для всех `TgError`, включая `Io { sent: false }` (bot-api перезапускается), `Timeout`, `429`.
Друг получает «Не получилось принять файл», строка закрыта, повторную отправку придётся делать руками, а загрузка демки в 1-2 ГиБ повторно стоит дорого.
**Fix:** для `Timeout`/`Io`/`Api 429/5xx` вернуть строку в `pending` с отсрочкой (новая колонка `next_try_ms` или `updated_at`-порог в `claim_pending`),
после нескольких попыток отвергать; отвергать сразу только `400/403/404`.

### WR-06: Скачанный файл остаётся в папке bot-api при отказах после `getFile`

**File:** `crates/server/src/bot/ingest.rs:756-781`
**Issue:** оригинал удаляется только после успешного `submit` (и при «не похоже на демку»). При `PATH_REJECTED` (несовпадение размера),
при ошибке записи/диска («сервер не смог принять файл»), при падении между `submit` и `remove_file` файл (до `max_demo_mib`, 2000 МиБ по умолчанию)
лежит в рабочей папке bot-api, и его никто не уберёт (в локальном режиме bot-api сам файлы не чистит). Повторные сбои на полном диске
съедают диск быстрее всего.
**Fix:** завести единый путь очистки: после успешного `safe_local_path` удалять оригинал в любой ветке выхода (guard со `Drop` или `finally`-подобный блок),
для случая `размер не совпал` тоже удалять файл, если он внутри корня.

### WR-07: Любая ошибка `?` в `ingest_once` навсегда оставляет строку в `downloading`

**File:** `crates/server/src/bot/ingest.rs:686-792`, `crates/server/src/bot/store.rs:155-179`
**Issue:** строка переведена в `downloading` до работы; дальше десяток `?` (`own_job`, `find_duplicate`, `known_file`, `demo_file`, `other_duplicate`,
`remember_file`, `mark_queued`). Ошибка на любом из них (в том числе кратковременная `database is locked`) возвращает `Err` потоку, а строка остаётся
`downloading` до перезапуска сервера (`recover`). Она при этом считается в лимитах `admit` (`state IN ('pending','downloading')`): друг упирается в «У вас уже 2 активные задачи»,
пока сервер не перезапустят. Хуже всего порядок в `queue_row`: `remember_file(...)?` (необязательный кэш) стоит **перед** `mark_queued`, поэтому сбой кэша после
успешного `Core::submit` оставляет в очереди задачу без `tg_jobs`, то есть без уведомлений и доставки до перезапуска.
**Fix:** обернуть тело в функцию, а при `Err` переводить строку обратно в `pending` (или в `rejected` с причиной);
в `queue_row` вызывать `mark_queued` первым, а `remember_file` — после и с `warn` вместо `?`.

### WR-08: `/resend` по `file_id` синхронно блокирует поток опроса на срок передачи

**File:** `crates/server/src/bot/deliver.rs:299, 324-369`; `crates/server/src/tg/http.rs:596-606, 373-377`
**Issue:** `resend_by_id` зовёт `send_video` из потока `bot-poll`, а `send_video` идёт через агент `transfer` с `timeout_recv_response` = 1 час по умолчанию.
Комментарий считает вызов быстрым, но при зависании bot-api/Telegram весь опрос (включая команды админа и приём новых файлов) стоит до часа.
**Fix:** не слать из потока опроса: помечать доставку `pending` (с `result_file_id`) и пусть отправляет `deliver_once`, который уже умеет слать `InputFile::Id`,
если `result_file_id` известен.

### WR-09: Отчёт админам занимается до отправки и теряется целиком при сбое

**File:** `crates/server/src/bot/notify.rs:478-509`
**Issue:** `claim_admin_report` ставит `admin_reported_ms` раньше отправки. Если `list_users` вернул ошибку, если ни у одного админа нет `tg_id` (админ заведён оператором без Telegram),
или `send_message` каждому не удался (сеть, 429), отчёт больше не повторится, и в журнале нет ни строки для случая «получателей нет». Для друга в соседней функции
сделан правильный откат (`unclaim_final` при точно недошедшем сообщении), для админа — нет.
**Fix:** снимать отметку, если ни одно сообщение не ушло (`unclaim_admin_report`), и писать `warn`, когда подходящих админов нет.

### WR-10: Ошибка записи итога доставки оставляет `sending` без повтора и без отчёта

**File:** `crates/server/src/bot/deliver.rs:130, 136`
**Issue:** `store::mark_sent(...)?` и `fail_delivery(...)?` пробрасывают ошибку записи в базу. Ролик при этом уже мог уйти, а строка осталась `sending`: ни `deliver_once`
(берёт только `pending`), ни тики её не трогают, друг не получает ни подтверждения, ни `uncertain`-сообщения, пока сервер не перезапустят (тогда молча станет `uncertain`, см. WR-02).
**Fix:** при ошибке записи итога повторить запись (короткий цикл 3 попытки) и в крайнем случае вызвать `mark_delivery(.., "uncertain", ..)` отдельным запросом и `tell(...)`;
не возвращать `Err` из `deliver_once` после того, как Telegram уже вызван.

### IN-06: 503 и 413 порождают отдельный поток на каждый отказанный запрос
