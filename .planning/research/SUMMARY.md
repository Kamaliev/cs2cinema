# Project Research Summary

**Project:** cs2cinema v1.1 «Сервер и Telegram-бот»
**Domain:** Telegram-бот + серверная очередь + удалённый раннер записи CS2 (расширение существующего Rust-приложения)
**Researched:** 2026-10-11
**Confidence:** MEDIUM-HIGH

## Executive Summary

v1.1 превращает ПК автора в удалённый рендер-раннер для белого списка друзей. Друг присылает боту демку (или ссылку FACEIT), Linux-сервер ставит задачу в очередь, раннер (приложение или `cs2-cli runner`) сам забирает её исходящим HTTPS-соединением и ведёт через неизменный `pipeline::job::run_job`. Готовый `highlights.mp4` раннер загружает на сервер, бот отправляет видео или объясняет сбой.

Рекомендованный путь: целиком синхронный стек без tokio, три новых крейта (`wire`, `server`, `runner`), сервер владеет намерением (кто, очередь, отмена, что сказать в чат), раннер владеет исполнением. Главные риски лежат не в самом боте, а в существующем коде, который до сих пор видел только демки автора: три дефекта должны быть закрыты до приёма первой чужой демки.

## Key Findings

### Recommended Stack

Подробности и версии — `STACK.md`.

**Core technologies:**
- `frankenstein` 0.52.1 (feature `client-ureq`) — блокирующий Telegram-клиент поверх уже имеющегося `ureq` 3; `teloxide` и hand-rolled отвергнуты
- `tiny_http` 0.12 за Tailscale Serve или Caddy — API раннера на `std::thread`; крейт мало развивается, запасной выход — `axum` 0.8 + `tokio` только внутри `crates/server`
- `rusqlite` 0.32.1 — строго версия воркспейса (другая версия конфликтует по `links = "sqlite3"`), миграции вручную через `user_version`
- `sha2` 0.10, `getrandom` 0.4, `ctrlc` — контрольные суммы, токены раннеров, корректное завершение в Docker
- `telegram-bot-api --local` в Docker (`aiogram/telegram-bot-api:10.3`) на Linux, общий том с `cs2-server`; лимиты 2 ГБ вместо 20/50 МБ
- Итого 34 новых крейта против 91–115 у стеков с axum или teloxide

### Expected Features

Подробности — `FEATURES.md`.

**Must have (table stakes):**
- Белый список Telegram-ID, незнакомцу показывается его ID; `/start`, `/help`
- `/player` (ник или SteamID64), игрок фиксируется в задаче при постановке
- Приём демки файлом с проверкой магических байтов; ссылка FACEIT (дёшево, разбор уже есть; ключ FACEIT остаётся на раннере)
- Позиция в очереди, `/status`, `/queue`, одно сообщение статуса, редактируемое с ограничением частоты
- Результат отдельным новым сообщением (правка не даёт push), понятный сбой без локальных путей
- `/cancel`, `/retry`, ограничения на пользователя, `/adduser`, `/removeuser`, `/users`
- Хранение и очистка файлов до появления первого друга

**Should have:**
- Одна демка на команду с задачей на игрока, обнаружение дублей по хешу
- Два уровня отчёта о сбое: друг видит человеческий текст, админ видит код, этап, подсказку, попытки
- Кнопка «Повторить» по сохранённой демке, `/pause`, `/resume`, уведомление «раннер офлайн»

**Defer / anti-features:** публичная регистрация, группы, несколько раннеров, ETA в секундах, сырые логи друзьям, ключ FACEIT на сервере, веб-панель.

### Architecture Approach

Подробности — `ARCHITECTURE.md`.

**Major components:**
1. `wire` — только serde-типы протокола (имя `wire`, не `proto`, из-за `crates/demo/proto`)
2. `server` (бинарник `cs2-server`) — бот, БД, API раннера, хранилище; не зависит от `pipeline`, `store`, `host`
3. `runner` — клиентский цикл, `Executor`, headless-исполнитель, outbox в `runner_state.json`
4. Режим раннера в приложении — удалённая задача как обычная строка `store` (миграция 6, `external_ref`), очередь, «Прервано», авто-повтор и пауза наследуются
5. Протокол: long-poll `claim` (до 25 с), POST прогресса = heartbeat (10 с) + доставка отмены; аренда 45 с с эпохой, потеря аренды мягкая и обратимая

### Critical Pitfalls

Подробности — `PITFALLS.md` (39 пунктов). Три дефекта существующего кода обязаны стать требованиями:

1. **Инъекция команд консоли.** Ник из демки (`Match::name` отдаёт `p.name.clone()`) попадает в `shot.title` и далее в комментарий `// Шот …` файла `highlights.cfg` (`renderer/src/lib.rs:207`) и в `drawtext` ffmpeg. Перевод строки превращает хвост в живые команды CS2. Проверено по коду при подготовке этого итога. Починить: очищать при построении `Match` и на входе `/player`, не класть текст из демки в cfg, `drawtext textfile=` с `expansion=none`, тесты на враждебных никами.
2. **Нет лимита размера и распаковки в `demo::read_demo`.** Файл читается целиком, `zstd decode_all` без потолка, разбор идёт в процессе раннера. Починить: потолки, проверка магии, разбор в дочернем процессе с лимитом памяти, ограничение числа повторных выдач (иначе цикл падений блокирует очередь).
3. **`pipeline::find_player` берёт первое совпадение подстроки.** Можно молча выбрать не того игрока. Починить: точное или единственное совпадение, `PLAYER_AMBIGUOUS` и `PLAYER_NOT_FOUND` со списком до 10 очищенных кандидатов до запуска CS2, закрепление по SteamID64.

Прочее: токен бота и раннеров не в журналах; белый список проверять до `getFile`; `sendVideo` может зависнуть без ответа — состояние `uncertain` без слепого повтора; раннер не должен быть службой Windows (CS2 нужна интерактивная сессия).

## Implications for Roadmap

### Phase 1: Протокол и ядро сервера
**Rationale:** все остальные части зависят от протокола и конечного автомата.
**Delivers:** `wire`, БД сервера с миграциями, автомат состояний с виртуальными часами, аренды с эпохой, атомарный claim (`BEGIN IMMEDIATE`), токены раннеров, блобы с докачкой, тестовая команда `submit`.
**Avoids:** гонки выдачи, потерянные результаты, зависшие аренды.

### Phase 2: Раннер, защита входа, первый живой прогон
**Delivers:** три исправления существующего кода (выше) и новые коды сбоев (`PLAYER_NOT_FOUND`, `PLAYER_AMBIGUOUS`, `NO_HIGHLIGHTS`, `BAD_DEMO`, `DEMO_TOO_LARGE`); крейт `runner`, `cs2-cli runner`, outbox, возобновление; проверка результата ffprobe (H.264, yuv420p, faststart); возврат в очередь сбоев класса «окружение».
**Note:** первый настоящий сквозной прогон записи; закрывает долг v1.0 (ACC-02/ACC-03) живой проверкой. Требуется короткий спайк по изоляции разбора.

### Phase 3: Telegram-бот и доставка
**Delivers:** спайк `telegram-bot-api --local` (общий том, права, `file://`), `FakeTelegram`, `authorize()` до `getFile`, приём, команды, объединение правок статуса, `uncertain` и `/resend`, двухуровневые тексты сбоев, `redact()`. Может идти параллельно с фазой 2.

### Phase 4: Режим раннера в приложении
**Delivers:** миграция 6, хук `on_settled` в `queue.rs`, `LocalQueueExecutor`, обёртка прогресса, страница настроек, авто-возобновление «Прервано». Наибольший риск регрессий: сначала прочитать тесты `queue.rs`.

### Phase 5: Хранение, защита, развёртывание, сквозные учения
**Delivers:** уборщик файлов, лимиты на пользователя, набор враждебных входов, аудит токенов, документация развёртывания (systemd, Tailscale, резервные копии), учения (убить раннер посреди записи, обрыв загрузки, перезапуск сервера, отмена при офлайн-раннере, 500 МБ через прокси, несовпадение версий), сквозной тест с фейковым Telegram, CI-задача на Linux.

### Research Flags

Нужны спайки: локальный Bot API (права на общий том, таймауты `getFile`/`send*` на 0,5–1,5 ГБ, `sendVideo` против `sendDocument`); `tiny_http` под 8 МиБ `PUT`, `Expect: 100-continue`, обрывы; изоляция разбора дочерним процессом с Job Object; Tailscale unattended на Windows.

## Расхождения исследований и решение

- **Загрузка результата:** `ARCHITECTURE.md` — `HEAD` + один потоковый `PUT`; `STACK.md` — куски по 8 МиБ. Принято по `STACK.md` (у `ureq` нет таймаута простоя, зависшая загрузка занимала бы поток `tiny_http`).
- **tokio:** принят синхронный вариант, `axum` — запасной выход только внутри `crates/server`.
- **Зависимости `runner`:** нужны `pipeline` и `host` (по `ARCHITECTURE.md`); `wire` и `server` от них не зависят.
- **Ссылки FACEIT:** `FEATURES.md` — обязательно, `ARCHITECTURE.md` — по желанию, `PITFALLS.md` — риск SSRF. Предложение: включить в фазу 3, только на стороне раннера; подтвердить с автором.
- **Доступ к БД сервера:** актор-поток или `Arc<Mutex<Connection>>` — решить в начале фазы 1.
